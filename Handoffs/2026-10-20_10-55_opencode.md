## 1. Executive Summary

The QR sign-in feature (`eb3b8dc`) was **implemented and deployed**, but a verification pass
found it shipped with four defects and two latent design problems. All are now fixed, verified
live, and the branch is in a releasable state.

The headline finding: **the 5-character pair code had 5 bits of entropy, not 25.** The generator
walked a single 64-bit LCG and took `seed % 32` per character. Because the LCG's multiplier and
increment are both odd, the low 5 bits of every step depend only on the low 5 bits of the first
one — so all five characters were a function of 5 bits. Measured on the running server: **40
sessions produced 15 distinct codes**, against an intended space of 32⁵ = 33,554,432.

That matters because `POST /api/auth/qr/lookup` resolves a code to a live pairing session. Any
signed-in account (a viewer-role Google login is enough) could try all 32 codes in under a second
and hijack another user's active TV pairing, binding that television to the attacker's account.

**Current state: green suites, live-verified fix, service restarted on a new binary.**

## 2. What Was Wrong, and What Changed

### 2.1 Pair-code entropy collapse — P0, security

`rust/src/services/auth_service.rs` — `generate_pair_code()`.

All five characters now come from the OS CSPRNG (`getrandom`), drawn **independently**.
`byte % 32` is exactly uniform here (the charset is 32 characters and 256 is a multiple of 32),
so no rejection sampling is needed and there is no modulo bias — stated in a comment, because it
is the obvious reviewer question.

**Verified live: 200 sessions → 200 distinct codes** (was 40 → 15).

### 2.2 Predictable security tokens — P0, security

`generate_random_token()` hashed a clock-derived seed:
`nanos ^ counter ^ pid ^ (nanos_low64 ^ const)`. That seed is guessable to anyone who can narrow
the creation time to about a second. It mints `sess_` session tokens, `ms_` device tokens, the
OAuth `state` and `nonce`, the PKCE `verifier`, and the `qr_id`.

The `qr_id` deserves its own emphasis: it is the **only** key to
`GET /api/auth/qr/{id}/finalize`, which is unauthenticated and hands out a 30-day session cookie.

Now 256 bits from `getrandom`. The signature changed to `Result<String, AppError>` and all eight
call sites propagate with `?` — the compiler found every one.

### 2.3 Pair code and `qr_id` logged in plaintext — P0, security

`info!("QR: created pair session qr_id={} code={}")` handed an account-takeover token to every
log reader. The log now carries a 12-hex-character reference that is neither the code nor the
full id.

**Verified: the code and the full `qr_id` are both absent from `logs/rust_api.log`.**

### 2.4 Frontend suite regression — P0

`useQrSession` constructed an `EventSource` inside an effect, and **jsdom implements no
`EventSource`**. The resulting `ReferenceError` was thrown from an effect, which React treats as
fatal for that subtree — so it tore down the whole `AccountPage` tree and failed *every*
assertion in that file, not just the one that cared about the QR panel.

`web/src/test/setup.ts` now stubs it. That file is already the established home for exactly this
kind of stub (`play`, `pause`, `load`, `scrollTo`).

A second, independent break: the "Sign in with Admin PIN" button was renamed to a bare
"Admin PIN" and moved into the panel, while `AccountPage.test.tsx:73,335` asserts
`/sign in with admin pin/i`. The accessible name was **restored**.

### 2.5 The QR panel flashed for signed-in users

The panel was gated on `!authenticated` only, and `authenticated` is `false` for *everyone* while
`/api/auth/me` is in flight. So the panel mounted for signed-in users, flashed a "Sign in" card
at someone who was already signed in, and fired `POST /api/auth/qr` — **creating a pair session
on the server on every account-page visit by an authenticated user.**

Now gated on `!authLoading && !authenticated`.

### 2.6 StrictMode created two sessions per expiry

The countdown expiry check lived *inside* a `setSecondsLeft` updater and called `fetchSession()`
from there. A state updater must be pure, and React's StrictMode deliberately double-invokes
updaters in development — so every expiry created two pair sessions, one of them orphaned. The
expiry check now lives in the interval callback, where side effects belong.

### 2.7 The test suite wrote to the production database

Every Rust integration test built its config with `AppConfig::from_env()`, which falls back to
`postgresql://postgres:postgres@127.0.0.1:5432/media_server` when `MEDIA_SERVER_DATABASE_URL` is
unset — and on this host it is unset. The whole suite ran against the **live catalog**.

New `rust/src/test_support.rs`:

- `test_config()` provisions a dedicated **`media_server_test`** database (override with
  `MEDIA_SERVER_TEST_DATABASE_URL`), redirects `cache_dir` to a per-process temp path, and
  leaves `media_roots` alone so file-based contracts still work.
- `seed_real_media_row()` / `remove_seeded_media_row()` seed and remove a catalog row for a real,
  probeable media file.
- `discover_real_media_file()` finds one.

**Verified: the production database is now untouched by the suite.** The two residue rows the
earlier session left behind (created 09:30:24) were removed.

### 2.8 `ensure_schema()` created only 7 of the 13 tables

`movies`, `progress`, `devices`, `device_watch_history` and `ip_cache` came only from the
SQLite→PostgreSQL migration script, so a fresh database was half-formed — the server booted,
created its own tables, then failed on the first query that touched the catalog. The isolated test
database made this visible immediately.

Those tables are now created with DDL matching the migrated production tables exactly, so
`CREATE TABLE IF NOT EXISTS` is a no-op against the live database.

### 2.9 `qr_device_auth_flow_test` was not idempotent

It inserted `users(google_sub='sub_phone_user')` with a plain `INSERT` and never removed it, so it
passed on a clean database and then failed on **every** subsequent run with
`23505 duplicate key value violates unique constraint "users_google_sub_key"`.

It now has setup-time purging, an explicit async teardown hook, idempotent inserts, and a
residue assertion that checks the count is zero rather than trusting the hook.

### 2.10 A test asserted against a hardcoded production title

`scanner_engine_test` asserted that `Oculus.2013.1080p.BluRay.x264.YIFY.mp4` survived
reconciliation — so it broke if that title was ever removed from the library. It now owns its
fixture, and the same intent is asserted hermetically.

## 3b. Database Backup & Recovery (completed after the handoff was first written)

The backup runbook was found to document a **retired** system in full — `app/services/backup_service.py`,
`scripts/backup_database.py`, `scripts/restore_database.py` and `media.db` itself, none of which
exist any more. An operator following it would have found a runbook for a database that is not in
use.

**Delivered:**

- **`docs/BACKUP_AND_RESTORE.md` rewritten** for PostgreSQL 18.4: `pg_dump -Fc` backups, the
  restore procedure, the SQLite WAL hazard replaced by the real PostgreSQL hazards, what
  `ensure_schema()` does and does *not* repair after a restore, and the retired SQLite material
  retained in §8 as history.
- **`scripts/restore_postgres.ps1` (new)** — the restore tool did not exist; the old restore path
  was a decommissioned Python script. It verifies the archive is readable *before* touching
  anything, takes a pre-restore rollback point and **refuses to proceed if it cannot take one**,
  requires `-Confirm` to act, and reports row counts afterwards.
- **`MediaServerBackup` Scheduled Task (new)** — daily at 03:00, running as `SYSTEM`. Nothing on
  this host ran the backup automatically; the archives had been taken by hand.
  - `scripts/install_backup_task.ps1` / `.bat` — registers it (idempotent, self-elevating)
  - `scripts/run_backup_task.bat` — the wrapper, which appends to `logs\backup_postgres.log` and
    propagates the exit code. It exists because `backup_postgres.bat` ends with a `pause` that
    would hang a non-interactive scheduled run.
  - `scripts/uninstall_backup_task.ps1` — removes it
- **Rotation split** — scheduled backups and pre-restore rollback points are now pruned on
  separate budgets, so a rollback point can never displace a scheduled backup.

**Verified by a live drill against the production database:** backup → stop the service → restore
over the live database → restart. All eight checked tables matched (movies 33, users 3, sessions 13,
progress 8, devices 393, settings 3, auth_tokens 21), 13/13 tables restored, health 200 and the
public API 200 afterwards. The task was then triggered manually: *Last Result 0*, a valid
73-object archive produced, service unaffected.

> A non-elevated shell **cannot read the task** — `schtasks /query` returns *Access is denied*.
> That is correct for a SYSTEM-owned task, not a misconfiguration.

**Orphaned bytecode purged:** 168 `.pyc` files whose source modules no longer exist, across

## 5. Deliberately Not Done

These were discussed and explicitly deferred:

- **Plaintext `code` at rest.** The `device_pair_sessions` table stores both `code` and
  `code_hash`; only the hash is needed for lookup. Removing the plaintext column needs an
  `ALTER` on a live table. **Scheduled separately** (decision 2).
- **Pinning a public base URL.** `get_base_url` trusts `Host` and `X-Forwarded-Proto`, so the
  emitted `qr_url` is host-header-injectable and defaults to `https` even on a plain-HTTP origin.
  There is no `PUBLIC_BASE_URL` config to pin it to.
- **Binding `finalize` to the TV.** It is unauthenticated and keyed only on `qr_id`; a per-session
  secret issued at create time would close that.
- **Rate-limiting the QR endpoints / capping the SSE stream.** `/wait` spawns a task plus a
  PostgreSQL query every 3 seconds per connection, with no auth and no cap, on a public endpoint.
- **Adding `Secure` to the session cookie.** Pre-existing and codebase-wide — `auth.rs:345,405,424,467`
  are all identical — so it is a separate change, not a regression from this work.
- **Closing the public `:8000` origin forward.** `http://122.163.124.18:8000/health` answers 200
  from the internet, bypassing Caddy and TLS entirely. The router forwards 8000.
- **The stale `vite.config.ts` dev proxy.** It still points `/api` at the decommissioned Flask
  `:8000`, so `npm run dev` fails for every API call. Pre-existing.

## 6. Traps Worth Knowing

- **`getrandom` and `url` are already in `Cargo.lock`** (0.2.17 and 2.5.8, pulled in by
  `rand_core`/`ring` and `sqlx-core`/`tower-http`). Adding them as direct dependencies cost no
  additional compilation.
- **A state updater must be pure.** The StrictMode double-session bug came from a `fetchSession()`
  call inside `setSecondsLeft`. React double-invokes updaters in development on purpose.
- **An error thrown in an effect is fatal for that subtree.** That is why the missing `EventSource`
  failed every assertion in `AccountPage.test.tsx` rather than one.
- **`ensure_schema()` runs on every pool creation**, including the test pool, so a fresh test
  database self-provisions.
- **The Rust harness runs tests within a binary in parallel.** A setup-time purge that is too
  broad will delete a concurrently running test's rows — the pair-session purge is scoped to
  *expired* rows for that reason.
- **A test DB is not a licence to leave residue.** The seeded catalog rows and the
  `sub-pair-test` user are removed by explicit teardown.
- **A `.bat` that ends with `pause` will hang a Scheduled Task.** That is why the scheduled
  backup calls `run_backup_task.bat` rather than `backup_postgres.bat`.
- **A Scheduled Task registered for `SYSTEM` cannot be read by a non-elevated shell.**
  `schtasks /query` returns *Access is denied*. That is correct posture, not a fault.
- **The backup rotation and the rollback points must be pruned on separate budgets.** A
  rollback point is a full dump, so without the split it would occupy a slot in the scheduled
  rotation and could evict a scheduled backup.
