## 1. The responsive sweep (D7)

**The viewports** — the two the archived reference has, and three it did not: portrait (540 × 960 @2),
landscape (1920 × 1080 @1), ultrawide (2560 × 1080 @1), tablet (1024 × 1366 @2) and a modern phone
(1080 × 2400 @3).

**The web's half is pixel-exact.** The archived original is a standalone document that can be laid
out at **any** viewport, so the oracle puts it and the port side by side at all five and compares
them **pixel for pixel** — not "within a tolerance", the same picture. **All twelve oracle tests
pass**, and the three new aspects are exact.

**The Flutter client's half is exact too**, and it checks the things a frame comparison cannot:
the lockup's **arrangement** follows the breakpoint (asserted from the rendered geometry, so a
device that lies about what it is cannot get the wrong layout), the canonical's **clamps** hold, and
**nothing overflows**. Its **parameters** are asserted against the canonical's fixture at each
aspect's design unit.

> **The frame is aspect-independent except for one field.** The lockup's vertical travel is
> `pl · u · 2.4`, so the fixture now carries the travel for **each design unit** the sweep visits
> (5.4, 10.24, 10.8), and the Flutter client is asserted against the one for its own aspect.

## 2. The re-capture — and the claim the plan assumed is not achievable

The plan said the re-captured frames would become "a byte oracle everywhere". **They cannot be**, and
the reason is worth recording: the archived frames were captured in a **different browser**, and two
things rasterise differently there —

* the SVG grain's turbulence, which is **1–2 units over the whole frame**, and
* the **Gaussian blur** on the wordmarks, which is a large delta on the glyph edges, over a tiny
  area.

Neither is a design difference, and the web's own oracle (which compares the archived original and
the port **in the same browser**) is unaffected. So the re-capture proves the two things that *can*
be proved:

| Claim | How | Measured |
|---|---|---|
| **Reproducible** | the capture is run twice; the two runs must be byte-identical **where the curtain is closed** — which is where the frames are a property of the overlay alone | the landscape **58/58**; the portrait **55/58** (three stragglers, in a bounded region on the blurred wordmark) |
| **Faithful** | the new frames are compared, pixel by pixel, with the archived ones, outside the shake and the parting | the landscape **0.013 %** of pixels differ by more than 32/255 and the mean error is **0.02**; the portrait **0.140 %** and **0.99** |

The metric is the same one the Flutter client's oracle uses, so the two are comparable. **The frames
are replaced only if the comparison passes** — and it did.

> **The frames after the parting show the live application, and it is not static between runs.**
> The application behind the curtain is a live client; its data arrives when it arrives. The
> closed-curtain window is the reference, and it is fully reproducible.

**One thing the capture had to be taught.** The first run produced frames that differed between
runs in the **subtitle's** region. The cause was a **font-loading race** — the application's
typeface arrives over the network, and a wordmark drawn before it lands is rasterised with the
fallback, which changes the *blurred* wordmark's edges. The capture now waits for
`document.fonts.ready` before the first frame, and the landscape went from 53/58 to **58/58**.

## 3. The offline renders

Both MP4s are re-encoded from the new frames, with the score, and the **keystills** are taken from
the frames too — so they can never drift from the videos. The encoder's paths were stale: it looked
for the score and the frames **beside the script**, where they have never been. It now reads them
from the artefacts directory, and it writes the stills itself.

**The videos are archival now.** The Flutter client was described as their consumer; since Slice
11.5 it ships the **WAV** and never played a video.

## 4. A correction to the plan — and a real fix

The plan said the archived tooling pointed at a retired port. **It does not**: **`:8001` is the
injection proxy's own port** (`serve_with_intro.py`, which forwards to the app on `:8000`), and the
archived pipeline is consistent about it.

**The genuinely broken thing was the dev server's proxy.** It pointed its "Rust" routes at `:8001`
— where nothing runs — and its "Flask" routes at `:8000`, which *is* the Rust service. The two were
**the wrong way round**, and **every `/api/movies` call through the dev server was failing** with
`ECONNREFUSED` while filling the log. There is now **one origin**, and the dev server's API works:

```
localhost:5173/api/health     -> HTTP 200
localhost:5173/api/movies     -> HTTP 200, 26,174 bytes (the real library)
localhost:5173/api/transcodes -> HTTP 200
```

**Caddy and `media.anisparvez.in` are untouched** — the change is `web/vite.config.ts`, which only
the dev server reads. Verified: the Rust service on `:8000` answers 200, Caddy is serving on 443 as
`caddy_custom`, and `https://media.anisparvez.in/api/health` returns 200.

> **One more thing worth knowing:** the dev server binds the **IPv6 loopback** (`::1`), so it is
> reachable at `http://localhost:5173` and **not** at `http://127.0.0.1:5173`.
