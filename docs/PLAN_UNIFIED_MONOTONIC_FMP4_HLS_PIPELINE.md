# Implementation Plan: Unified Monotonic fMP4 HLS Pipeline & Android Client Timestamp Fix

## 1. Context & Root Cause Analysis

### 1.1 Observed Defect
When watching *Verity* (`Verity 2026 1080p WEB-DL HEVC x265 5.1 BONE.mkv`) on Direct Play in the Android app (AHMS) at position `50:31` (`3031s`), switching quality in-flight to 1080p transcoded HLS results in no video or audio playback. The screen remains static at `50:31`, while the network speed indicator displays continuous 3–4 MB/s cellular download traffic for 20+ seconds until the app is closed.

### 1.2 Exhaustive Root Cause Verification
1. **Multi-Chunk Relative Timestamps (`tfdt: 0`)**:
   - In `rust/src/services/media_pipeline/transcode_worker.rs`, the dual-GPU transcoding pipeline partitions the video into 60-second chunks (`-ss chunk.start_time -t chunk.duration`).
   - FFmpeg's `hls` muxer generates fragmented MP4 (`.m4s`) media segments whose internal `tfdt` (`Track Fragment Decode Time`) box contains timestamps starting at `0.0s` relative to the chunk start, regardless of `-output_ts_offset`.
   - FFmpeg writes the chunk offset (e.g. 3000s for Chunk 50) exclusively into the `elst` (edit list) box of each chunk's `init_chunk_{id}.mp4` initialization segment.
2. **FFmpeg / `libmpv` Skips Redundant Initialization Headers**:
   - When `libmpv` (via FFmpeg's `libavformat/hls.c` and `mov.c`) opens `playlist.m3u8`, it first reads `init_chunk_0.mp4` from the top of the playlist to initialize the stream formats (`elst: 0`).
   - When seeking to `50:31` (`3031s`), `hls.c` seeks to Chunk 50 and reads `init_chunk_50.mp4`.
   - `mov.c` detects existing stream contexts and outputs: `[mov,mp4,m4a,3gp,3g2,mj2] Found duplicated MOOV Atom. Skipped it`. It discards `init_chunk_50.mp4` completely.
   - Consequently, the 3000s edit list offset is lost, leaving the stream anchored to `0.0s`.
3. **The Fatal Demuxer Property (`use_tfdt=0`)**:
   - In `flutter_client/lib/features/player/data/media_kit_player_adapter.dart`, `demuxer-lavf-o: seg_format_options=use_tfdt=0` was configured.
   - This flag explicitly forces FFmpeg to ignore the `tfdt` box in all fragments.
   - With both `elst` and `tfdt` bypassed, all packets decode with presentation timestamps from 0s to 58s.
   - Because `libmpv` was instructed to seek to `3031s`, every incoming packet is evaluated as stale (`pts < 3031s`) and discarded.
   - `libmpv` loops through all subsequent segments from Chunk 50 to Chunk 120 (the end of the movie), downloading 3–4 MB/s continuously without ever finding packets matching `3031s`.

### 1.3 Verified Mathematical Proof
We performed a binary modification on `segment_001606.m4s` (Chunk 50), adding the true chunk timeline offset (`3000s * timescale`) directly to the `baseMediaDecodeTime` in its `tfdt` box, and tested playback using `init_chunk_0.mp4`:
- Video packets decoded with true monotonic timestamps: `pts_time = 3025.000407` to `3025.167074`.
- Probing with `ffmpeg -i test_monotonic.m3u8 -frames:v 5 -f null -` decoded keyframes in **50 milliseconds** with **zero errors**, **zero duplicated MOOV warnings**, and **zero dropped frames**.

## 2. Scope

### 2.1 Backend (`rust/`)
- **`transcode_worker.rs`**:
  - Implement a fast in-place binary `tfdt` stamper function `stamp_segment_tfdt(segment_path, chunk_start_time, video_timescale, audio_timescale)` executed immediately as each `.m4s` segment is written.
  - This guarantees every `.m4s` fragment generated by any GPU chunk worker carries monotonic presentation timestamps matching the movie timeline.
- **`chunk_transcode.rs`**:
  - In `update_master_playlist`, unify the playlist under a single canonical initialization map `#EXT-X-MAP:URI="init.mp4"` (or `init_chunk_0.mp4`).
  - Eliminate redundant `#EXT-X-DISCONTINUITY` and duplicate `#EXT-X-MAP` tags for monotonic fMP4 streams.
- **Cache Reconciliation**:
  - Provide and execute a utility script to stamp the existing *Verity* 1080p segments in `E:\MediaServer\cache\hls\b21b19570b9595b52af09d004e2daa8dc57163b4f38a516d6353a6a24d9aa0d4\1080p\` and update its `playlist.m3u8` to the clean monotonic format so the user's current session works immediately without waiting for re-transcoding.

### 2.2 Frontend (`flutter_client/`)
- **`media_kit_player_adapter.dart`**:
  - Completely remove `_configureNativeDemuxer()` and its `demuxer-lavf-o: seg_format_options=use_tfdt=0` option.
  - Retain clean pipeline lifecycle management (`player.stop()` prior to `open()`, native `start` position setting, watchdog with buffering guards).
- **`hls_seek_and_resume_test.dart`**:
  - Update tests to verify that `use_tfdt=0` is not present and that monotonic HLS playback initializes seamlessly.

### 2.3 Deliberately Unchanged
- RFC 7233 byte-range Direct Play remains untouched.
- Quality ladder resolution rungs and transcode profiles remain unchanged.
- React 19 SPA frontend remains fully compatible.
- PostgreSQL database schemas and REST API contract shapes remain unchanged.

## 4. Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| **`tfdt` atom version variations (version 0 vs version 1)** | The binary stamper reads `version = data[pos + 4]`. If `version == 1`, it writes an 8-byte 64-bit integer (`>Q`); if `version == 0`, it writes a 4-byte 32-bit integer (`>I`). |
| **Multi-track timescale differences** | The stamper identifies each track fragment by examining the `tfhd` `track_id` (track 1 = video @ 12288, track 2 = audio @ 48000) and applies the corresponding `chunk_start * timescale` offset. |
| **Existing transcode cache invalidation** | In-place stamping script reconciles *Verity*'s 1080p cached files directly in seconds, avoiding a lengthy 2-hour re-transcode. |
| **Service disruption during build** | `MediaServerRust` is updated cleanly via standard binary replacement or NSSM restart. |

---

## 5. Open Decisions
- None. Monotonic fMP4 packaging is the standard RFC 8216 specification and provides native compatibility for both HLS.js and native `libavformat`/`libmpv` players.
